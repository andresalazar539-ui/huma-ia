# FICHA DO PROVEDOR: InfinitePay, Vindi, Superlógica, Asaas

Pesquisa de 2026-11-06. Método: WebSearch + WebFetch nas docs oficiais; onde a doc oficial é renderizada por JavaScript (Superlógica: Postman publicado) ou bloqueava fetch, lida pelo Chrome. Cada item traz a URL da fonte. "NÃO ENCONTRADO NA DOC" = não existe na documentação oficial consultada.

Caso de uso: uma IA no WhatsApp precisa (a) quando o cliente digita o CPF, listar as cobranças EM ABERTO/vencidas dele com valor, vencimento e link de pagamento (segunda via/Pix), (b) enviar lembrete antes do vencimento, (c) receber webhook de pagamento confirmado, e (d) no InfinitePay, gerar um link de pagamento (Pix/cartão) de um valor pra fechar uma venda.

## 1. InfinitePay (Checkout Integrado / links)

Fontes: https://www.infinitepay.io/checkout-documentacao (doc oficial), https://ajuda.infinitepay.io/pt-BR/articles/10766888-como-usar-o-checkout-da-infinitepay (Central de Ajuda), https://www.infinitepay.io/taxas, https://www.infinitepay.io/desenvolvedores. Terceiros usados só pra lacunas: https://github.com/AlfaStage/wc-infinitepay (plugin WooCommerce), https://pub.dev/documentation/ms_infinitepay/latest/ (lib Dart), https://github.com/alminidev/NIX/issues/8 (issue que compara doc x ajuda).

1. **Autenticação**: API Key opcional no header `X-Api-Key: inchk_...` (prefixo `inchk_`, mostrada UMA vez, até 5 chaves ativas, "somente no seu servidor"). Sem chave, basta enviar o `handle` (InfiniteTag sem `$`) no corpo. A chave é exigida só pro objeto `options` e pro `/payment_check`. Onde pegar: App InfinitePay > Vendas > Checkout > aba Configurações > "Habilitar Checkout Integrado" > criar API Key; ou na web em https://app.infinitepay.io/external-checkout#configuracoes. **Sandbox: NÃO EXISTE** ("Não. O botão Testar API da documentação cria um link real na sua conta"); o jeito de testar é link real de R$ 1,00 apontando `redirect_url`/`webhook_url` pra endpoints de teste e estornar no app. (doc + ajuda)
2. **URL base**: `https://api.checkout.infinitepay.io` (doc oficial). Plugins/libs antigos usam `https://api.infinitepay.io/invoices/public/checkout/{links,payment_check}` (ms_infinitepay no pub.dev; wc-infinitepay no GitHub), caminho legado não documentado.
3. **Validar credencial**: NÃO ENCONTRADO NA DOC (não há endpoint "me"). Na prática: `POST /links` com `handle` + `X-Api-Key`; erro `external_checkout_not_enabled` = "Habilitar checkout integrado" desligado ou handle errado; `403` = API Key e handle de contas diferentes (doc).
4. **Buscar cliente por CPF/CNPJ**: NÃO EXISTE. A API não tem cadastro de clientes nem consulta de cobranças por documento.
5. **Listar cobranças de um cliente por status**: NÃO EXISTE. Só há `POST /payment_check` por link individual (body `handle`, `order_nsu`, `transaction_nsu`, `slug`; resposta `success`, `paid`, `amount`, `paid_amount`, `installments`, `capture_method`; "quando algo não bate: a API responde 200 com success: false ou paid: false"). `amount` = valor original em centavos, `paid_amount` pode ser maior quando as taxas são repassadas ("não exija que batam"). (doc)
6. **Link/boleto/Pix/segunda via**: o próprio link de checkout é a "fatura" (`checkout.infinitepay.io/<handle>/<slug>`); Pix e cartão são escolhidos dentro da página. Não há boleto nem endpoint de Pix copia e cola. (doc)
7. **Criar link de valor avulso**: `POST https://api.checkout.infinitepay.io/links`, body mínimo:
   ```json
   {"handle": "sualoja", "items": [{"quantity": 1, "price": 1000, "description": "Produto exemplo"}]}
   ```
   (preço em centavos, mínimo R$ 1,00: "O mínimo vale pra qualquer pagamento, inclusive links criados pela API e Pix"). Opcionais: `order_nsu` (gerado se omitido), `redirect_url`, `webhook_url` (string, formato da doc) ou `webhook: {"url": "...", "events": ["paid","refunded","canceled"]}` (formato da ajuda), `customer {name, email, phone_number}`, `address {cep, street, number, neighborhood, city, state, complement}`, `options` (exige API Key: `single_payment` bool "com true, o link aceita apenas um pagamento"; `valid_until` ISO 8601, no futuro e até 1 ano da criação; `payment_methods_enabled: ["credit_card","pix"]`, cartão sempre ligado, só o Pix é opcional; `discounts {"pix": 5, "credit_card": 2.5}` em %, >0 e <100; `assured_installments` 0-12 (até quantas parcelas o vendedor absorve a taxa; 0 = repassa tudo); `require_delivery_address` bool). **Resposta: a doc só diz "Leve o comprador até a URL do link que vem na resposta"; o nome do campo NÃO ESTÁ NA DOC.** O plugin WooCommerce de terceiro lê `$body['url'] ?? $body['payment_url']` e o issue alminidev/NIX cita `checkout_url` em spec não oficial: testar com link real. Após pagar, o comprador volta na `redirect_url` com `receipt_url`, `order_nsu`, `slug`, `capture_method` (credit_card|pix), `transaction_nsu` (a doc trata esses parâmetros como não confiáveis: confirmar via `/payment_check`). Parcelas: sem limite configurável, o checkout mostra até 12x desde que cada parcela fique em pelo menos R$ 1,00. (doc)
8. **Webhook**: definido por link na criação (não editável depois). Eventos: `created`, `paid`, `settled`, `canceled`, `refunded`, `payment_failed`. Payload (exemplo `paid`):
   ```json
   {"invoice_slug": "abc123", "amount": 1000, "paid_amount": 1010, "installments": 1, "capture_method": "credit_card", "transaction_nsu": "UUID", "order_nsu": "UUID-do-pedido", "receipt_url": "https://comprovante.com/123", "items": []}
   ```
   Responder 200 "de preferência em menos de 1 segundo"; "qualquer status fora de 2xx é falha e a entrega é tentada novamente. Para erro, o recomendado é 400" (sem contagem/intervalo publicados). **Sem assinatura/HMAC** ("não tem assinatura"): a doc manda confirmar com `/payment_check` antes de dar baixa. Formato dos eventos que não são `paid`: não documentado. (doc)
9. **Rate limit**: NÃO ENCONTRADO NA DOC. **Custo**: integração gratuita ("As únicas taxas são as taxas padrão de pagamentos"); Pix 0%; cartão no link de pagamento: plano "Em 1 dia útil" à vista 4,20% até 16,66% em 12x (faixa inicial) e 2,29% / 5,39% na faixa de maior faturamento; "Na hora" 5,49% / 18,29% (a página /taxas mostra duas tabelas conflitantes, conferir ao vivo). **Plano**: qualquer conta InfinitePay com "Habilitar checkout integrado" ligado; sem mensalidade.
10. **Pegadinhas**: sem sandbox; sem consulta por CPF; sem boleto; `amount` ≠ `paid_amount` quando o comprador paga juros; divergência entre doc (`webhook_url`) e ajuda (`webhook{url,events}`): aceitar os dois; doc grafa "itens" num trecho e `items` no payload (usar `items`); parcelas sem teto configurável; nome do campo da URL na resposta não documentado; webhook sem assinatura exige `/payment_check` com API Key; chave e handle precisam ser da mesma conta (403).
11. **Veredito**: **SIM**, token colado é viável (chave `inchk_` criada em 3 toques no app) e até opcional: só a InfiniteTag já cria link. Mas o produto cobre só (d) gerar link de venda + webhook; (a), (b) e (c) por CPF não existem.

## 2. Vindi (Recorrência, API v1)

Fontes: https://developers.vindi.com.br/reference/segurança-e-autenticação, https://developers.vindi.com.br/reference/criando-uma-chave-de-acesso, https://developers.vindi.com.br/reference/especificações-técnicas, https://developers.vindi.com.br/reference/getv1customers-1, https://developers.vindi.com.br/reference/getv1bills-1, https://developers.vindi.com.br/reference/getv1billsid-1, https://developers.vindi.com.br/reference/getv1chargesid-1, https://developers.vindi.com.br/reference/getv1userscurrent-1, https://developers.vindi.com.br/reference/buscas-e-filtros-1, https://developers.vindi.com.br/reference/rate-limit, https://developers.vindi.com.br/reference/webhooks-configurações, https://developers.vindi.com.br/reference/webhooks-conteúdo-da-requisição-e-eventos, https://developers.vindi.com.br/reference/payload-dos-webhooks, https://developers.vindi.com.br/reference/webhooks-segurança-e-testes, https://developers.vindi.com.br/reference/webhooks-retentativas-1, https://developers.vindi.com.br/reference/webhooks-formatos-e-métodos-de-envio, https://developers.vindi.com.br/reference/ips-utilizados-na-vindi-para-enviar-webhooks-1, https://developers.vindi.com.br/docs/sandbox-testes, https://developers.vindi.com.br/docs/assinatura-pix, https://vindi.com.br/precos/. (Índice de slugs: https://developers.vindi.com.br/reference ; cada página também existe como `.md`.)

1. **Autenticação**: HTTP Basic com a chave como usuário e senha vazia ("A autenticação na API é realizada através do método HTTP Basic"; curl `-u API_KEY:`; "o separador ':' continua obrigatório"), ou seja `Authorization: Basic base64("API_KEY:")`. Só HTTPS (HTTP não redireciona), TLS 1.2 explícito. Onde pegar: painel > **Configurações > Dados da empresa > aba "API & Webhooks" > "Chaves de Acesso" > "Nova Chave"** (nomear; "será exibida apenas uma vez"). **Sandbox**: app.vindi.com.br > Configurações > Sandbox > "Criar sandbox" (só administrador da plataforma; "É permitido apenas um sandbox por conta ativa"; "A utilização do ambiente sandbox é gratuita"; transações não contam no uso mensal) > "Acessar sandbox"; API em `https://sandbox-app.vindi.com.br/api/v1` (todas as funções; boleto ainda não testável em sandbox; cartões de teste em https://portal-dev-vindi.readme.io/docs/modo-trial-e-sandbox-quais-n%C3%BAmeros-de-cart%C3%B5es-posso-usar-para-teste). Sandbox exige conta com plano.
2. **URL base**: produção `https://app.vindi.com.br/api/v1`; sandbox `https://sandbox-app.vindi.com.br/api/v1` (staging `app.vindi-dev.com/api`, interno). `Content-Type: application/json` em POST/PUT ("A plataforma Vindi não suporta parâmetros no formato form-data ou x-www-form-urlencoded"). Respostas só JSON; valores monetários voltam como string.
3. **Validar credencial**: `GET /v1/users/current` ("Retorna o usuário atual": `id`, `name`, `base_role`); a doc lista só 200/400/422, 401 em chave inválida não está documentado: conferir em sandbox. Alternativa: `GET /v1/merchants/current`.
4. **Buscar cliente por CPF/CNPJ**: `GET /v1/customers?query=registry_code=12345678900` (campo `registry_code` = "CPF ou CNPJ"). Sintaxe de `query` (buscas-e-filtros): `query=<atributo><op><valor>`; operadores `:` contém (sem acento/caixa), `=` igual (aspas se houver espaço), `>`, `>=`, `<`, `<=`, `NOT`/`-` negação, `()` agrupamento, `AND`/`OR` (omitido = AND); valor URL-encoded. Parâmetros: `page` (1), `per_page` (25), `query`, `sort_by` (`id`, `name`, `status`, `code`, `email`, `registry_code`, `created_at`, `updated_at`), `sort_order` (asc|desc). Resposta (array de Customer): `id`, `name`, `email`, `registry_code`, `code`, `status` (active|inactive|archived), `notes`, `metadata`, `address {street, number, additional_details, zipcode, neighborhood, city, state, country}`, `phones[] {id, phone_type mobile|landline, number E.164, extension}`. Erros 400 (JSON inválido) e 422 (parâmetro inválido).
5. **Listar faturas por status**: `GET /v1/bills?query=customer_id=123 AND status=pending` (atributos pesquisáveis: `customer_id`, `status`, `due_at`, `subscription_id`, `period_id`, `code`, etc.; `sort_by` aceita `due_at`, `status`, `customer_id`, `amount`...). Status da fatura: `review`, `pending`, `paid`, `canceled`, `scheduled`; **não existe status "overdue" na fatura**: vencida = `status=pending AND due_at<"2026-11-06"` (datas: "Se o horário não for informado, consideraremos 00:00:00"; exemplo da doc `paid_at=>"2019-01-01" AND paid_at<="2019-01-03 23:59:59"`). Campos da Bill: `id` ("ID da fatura"), `amount` ("Valor da fatura"), `status`, `due_at` ("Data de vencimento da fatura"), `url` ("URL para pagamento da fatura"), `customer {id, name, email, code}`, `charges[]` (BillCharge: `id`, `status` pending|paid|canceled|processing|fraud_review, `due_at`, `amount`, `payment_method {id, public_name, name, code, type}`, `print_url` = "URL para impressão da cobrança. Usado apenas para boletos", `last_transaction {gateway_response_fields}` = "Atributos de resposta específicos do gateway"), `bill_items[]`, `payment_profile`.
6. **Link/boleto/Pix/segunda via**: a segunda via universal é `bill.url` (página hospedada da fatura, ex. `https://app.vindi.com.br/customer/bills/{id}?token=...`, mostra boleto / Pix QR / copia e cola conforme o método; nos docs de assinatura Pix: "O link para pagamento da fatura é retornado na resposta da requisição de criação da assinatura" e o link contém "um QR Code ou chave Pix"). Boleto: `charges[].print_url`; no payload Bolepix `gateway_response_fields` traz `typeable_barcode` (linha digitável), `print_url`, `url_payment`, `transaction_id`, `tid`, `date_payment`, `paid_amount`. Pix: a referência tipa `gateway_response_fields` como string sem chaves; nos exemplos de webhook `charge_created` (Pix/Bolepix pendente) aparece `qrcode_original_path` (payload copia e cola) e `qrcode_path`; `GET /v1/bills/{id}` e `GET /v1/charges/{id}` devolvem o mesmo objeto. No cartão de crédito `gateway_response_fields` contém só `nsu`. Não há endpoint dedicado "pixQrCode": NÃO ENCONTRADO NA DOC além dos exemplos. Validade do QR Pix: 24 h por padrão (FAQ Pix).
7. (não se aplica; Vindi tem link de pagamento no produto Commerce/Yapay, fora do escopo; a página "consultar-cliente" do Commerce é `POST /v1/people/get_person_by_cpf_and_email` em `api.intermediador.sandbox.yapay.com.br`, outra API)
8. **Webhooks**: painel > **Configurações > Webhooks > "Novo Webhook"** (URL + "Selecione todos os eventos que você deseja receber"; a Vindi faz uma requisição de verificação e só salva se responder 2XX). Eventos (`event.type` → `data`): `subscription_created/canceled/reactivated` (subscription), `charge_created/refunded/canceled/rejected` (charge), `bill_created`, `bill_paid`, `bill_canceled`, `bill_seen`, `bill_overdue` (bill), `period_created`, `issue_created`, `payment_profile_created/renewed`, `message_seen`, `invoice_issued`. Envio: `POST`, `Content-Type: application/json; charset=UTF-8`, `User-Agent: Vindi-Hookshot/1.0`, corpo:
   ```json
   {"event": {"type": "bill_paid", "created_at": "...", "data": {"bill": {"id": 16030001, "amount": "100.0", "due_at": "...", "status": "paid", "url": "https://.../customer/bills/16030001?token=...", "customer": {"id": 1, "name": "...", "email": "...", "code": "..."}, "charges": [{"print_url": null, "last_transaction": {"gateway_response_fields": {"typeable_barcode": "...", "print_url": "...", "url_payment": "..."}}}]}}}}
   ```
   ("O conteúdo do atributo data irá depender do tipo de evento enviado e respeitará o mesmo formato da API REST"; os exemplos "podem sofrer alterações nos dados retornados nos campos".) **Validação: sem HMAC**; a doc manda usuário:senha na URL (`https://usuario:senha@www.empresa.com/webhook`) ou `?secret=` validado do seu lado; IPs de saída produção 3.230.209.106, 3.226.130.240 (AWS), 52.5.38.201, 52.7.247.138 (QuotaGuard); homologação 35.153.190.190, 34.224.250.183 ("podem mudar sem aviso", lista de 31/10/2019). Só portas 80/443, certificado não autoassinado, mTLS opcional, desligar CSRF no endpoint. Retentativas: "até 8 tentativas de envio" em ~48 h quando não houver 2XX; depois descarta (reenvio manual). Testar com RequestBin/ngrok.
9. **Rate limit**: "Por padrão, a plataforma Vindi possui um limite de 120 requisições por minuto" (headers `Rate-Limit-Limit`, `Rate-Limit-Remaining`, `Rate-Limit-Reset` em Unix UTC; 429 com `Retry-After`; "O limite contempla todos os tipos de requisição, inclusive requisições inválidas do tipo 422"). **Custo/plano** (vindi.com.br/precos): Essential R$ 299/mês não lista API; "Integração via API" aparece a partir do **Pro R$ 499/mês**; Premium & Corporate R$ 1.119/mês ("Desenvolvimento de integrações personalizadas via API"); Enterprise sob consulta; mais taxas por transação (cartão a partir de 2,75% em 30 dias ou 3,25% em 14 dias, Pix 0,95% mín. R$ 1,60, boleto R$ 2,99, + R$ 0,39 por transação aprovada). A página de preços tem metadados antigos: confirmar com a Vindi.
10. **Pegadinhas**: chave é por conta inteira (sem escopo read-only); busca é por `registry_code` exato como cadastrado (a doc não normaliza pontuação); fatura "vencida" é derivada (pending + due_at passado) embora exista o evento `bill_overdue`; Pix só documentado em exemplos de webhook; sandbox não gera boleto; webhook sem assinatura; API só em plano Pro+; `/users/current` sem 401 documentado.
11. **Veredito**: **SIM**. Chave em Configurações > Dados da empresa > API & Webhooks, cola e pronto; cobre (a), (b), (c). Restrição: cliente precisa estar em plano com API (Pro+).

## 3. Superlógica

Dois produtos com APIs diferentes. Fontes oficiais (Postman publicado, lidas no Chrome porque WebFetch/Jina só devolvem a introdução): https://apiassinaturas.superlogica.com/ (Assinaturas) e https://apicondominios.superlogica.com/ (Condomínios); https://assinaturas.superlogica.com/hc/pt-br/articles/360004013613-Como-criar-o-app-e-access-token; https://assinaturas.superlogica.com/hc/pt-br/articles/360008275514-Integra%C3%A7%C3%B5es-via-API; https://imobiliarias.superlogica.com/hc/pt-br/articles/12249428568855-Utiliza%C3%A7%C3%A3o-de-APIs-para-integra%C3%A7%C3%B5es-no-sistema-Superl%C3%B3gica; https://superlogica.com/recursos/webhooks-no-superlogica/; https://blog.superlogica.com/assinaturas/webhooks-mais-integracao-superlogica-com-outros-sistemas/; https://superlogica.com/api/api.pdf (PDF de 2013, API antiga `LICENCA.superlogica.net/financeiro/atual/`, só histórico); terceiros: https://docs.erathos.com/connectors/apis/superlogica (validade do token), https://kondado.com.br/blog/wiki/2021/06/21/superlogica/ (campos), https://glama.ai/mcp/servers/mcp-dir/superlogica-mcp (lista de 114 endpoints do Condomínios), https://github.com/atqjunior/segunda-via-boleto-superlogica (exemplo de 2ª via por CPF). Doc antiga no Apiary (https://superlogicaassinaturas.docs.apiary.io/) está descontinuada.

1. **Autenticação**: dois tokens fixos nos headers `app_token` e `access_token` (+ `Content-Type: application/x-www-form-urlencoded` no Assinaturas; `application/json` ou `application/x-www-form-urlencoded` no Condomínios; o Condomínios também aceita os tokens como query string em alguns exemplos). Onde pegar: menu do usuário (canto superior direito) > **Todos os usuários** > localizar o cadastro > **Aplicativos** > **Novo App Token** > nome e descrição > Salvar > copiar App Token e Access Token (Assinaturas); Condomínios: "Todos os usuários (canto superior direito) / API (Integração com outros sistemas) / Aplicativos / Novo App Token". Gerenciamento em https://superlogica.net/usuario (uma base de dados = um aplicativo; "Todo este processo segue o padrão OAUTH2" na prática é só token fixo). "O token vai herdar os acessos do usuário que criou"; exige perfil "1000 - Acesso Administrativo" ou "1061 - Configurações - Alteração" e módulo de configurações ativo. **Validade: "exatamente 1 ano a contar da data de geração"** (depois gera outro). **Sandbox Assinaturas**: trial em `trial.superlogica.com/?plataforma=dev-assinaturas` ("expira em 91 dias", prorrogável, com limites de segurança). **Condomínios**: trial em https://www.superlogica.com/condominios/ > "Experimente grátis" no plano Enterprise I ou acima.
2. **URL base**: Assinaturas `https://api.superlogica.net/v2/financeiro/`; Condomínios `https://api.superlogica.net/v2/condor/CONTROLLER/ACTION`. Datas `MM/DD/AAAA`; números com "." decimal, sem milhar, "-" negativo; "Atente-se ao case sensitive no envio dos parâmetros". Retorno JSON UTF-8; status ≥ 300 é erro. Paginação `pagina` (1) + `itensPorPagina` (padrão 50; Assinaturas: "Caso o valor seja maior que 200, a request será bloqueada"; Condomínios: "Limite máximo 50").
3. **Validar credencial**: NÃO ENCONTRADO NA DOC. Usar `GET /v2/financeiro/clientes?itensPorPagina=1` (Assinaturas) ou `GET /v2/condor/condominios/get?id=-1&somenteCondominiosAtivos=1` (Condomínios); 401/403 = "App ID ou Access Token incorretos, expirados ou mal informados" (artigo Integrações via API). Suporte só por e-mail api@superlogica.com (Imobiliárias: api.imobiliarias@superlogica.com).
4. **Buscar cliente por CPF/CNPJ**:
   - Assinaturas: `GET https://api.superlogica.net/v2/financeiro/clientes?pesquisa=46063327860&status=2&apenasColunasPrincipais=0` ("Consultar clientes"; `pesquisa`: "Procure pelo número do documento do cliente"; `status`: 0 Ativos, 1 Inativos, 2 Todos, 3 Congelados; `identificador` (identificador externo, "não é o id"), `comDiaDeVencimento`, `apenasPessoasJuridicas`, `comDadosDoGrupo`, `semClientesCongelados` (1 remove congelados), `posicaoEm` (data pra verificar adimplência, padrão hoje), `pagina`, `itensPorPagina`). Resposta: `id_sacado_sac`, `st_nome_sac`, `st_nomeref_sac`, `st_cgc_sac` (CPF/CNPJ), `st_email_sac`, `st_telefone_sac`, `st_celular_sac`, `st_diavencimento_sac`, `dt_cadastro_sac`, `dt_desativacao_sac`, `fl_status_sac`, `fl_pessoajuridica_sac`, `id_grupo_grp`. Há também "Consultar cliente com ID".
   - Condomínios: `GET https://api.superlogica.net/v2/condor/unidades/index?idCondominio=-1&pesquisa=31735008656&exibirDadosDosContatos=1&exibirInadimplencia=1&exibirGruposDasUnidades=1` ("Listar unidades de um condomínio"; `idCondominio`: "Use -1 para buscar em todos"; `pesquisa`: "Pesquisa pelo valor passado(CPF, Celular, Email, Nome)"; `exibirInadimplencia=1` "Exibe as inadimplências por unidade"). Devolve a unidade (`id_unidade_uni`, `st_unidade_uni`, `st_bloco_uni`, `id_condominio_cond`, `st_nome_cond`, `fl_statusfin_uni`) e contatos (`id_contato_con`, `st_nome_con`, `st_email_con`, `st_telefone_con`). Lista de condomínios: `GET /v2/condor/condominios/get?id=-1&somenteCondominiosAtivos=1&ignorarCondominioModelo=1&apenasColunasPrincipais=1` (`id_condominio_cond`, `st_nome_cond`, `st_fantasia_cond`, `st_cpf_cond` = CNPJ do condomínio).
5. **Listar cobranças por status**:
