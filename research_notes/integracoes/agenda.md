# FICHA DO PROVEDOR: agendas para a HUMA (Feegow, Clínica nas Nuvens, Trinks, Calendly, Microsoft Graph)

Fatos lidos nas docs oficiais em 2026-11-06. Quando a doc não diz, está marcado "NÃO ENCONTRADO NA DOC". Referência de comparação: hoje a HUMA usa Google Calendar (FreeBusy + events.insert) em `huma/services/scheduling_service.py`.

Caso de uso: uma IA no WhatsApp precisa (a) consultar horários LIVRES de um profissional num intervalo (ou listar slots disponíveis), (b) criar o agendamento com nome, telefone e serviço, (c) cancelar/remarcar, (d) receber webhook de cancelamento/alteração.

## 1. Feegow (clínicas)

1. **Autenticação**: token estático gerado no painel. Caminho (Central de Ajuda): **Configurações → Outras Configurações → API Pública → "Gerar novo Token"**; só usuário administrador acessa; depois de gerar, lápis = nome, cadeado = permissões; recomendam um token por sistema integrado (https://ajuda.feegow.com/support/solutions/articles/67000714396-como-integrar-o-feegow-via-api-com-outros-sistemas-). Header exato: `x-access-token: <token>` (https://docs.feegow.com/). Validade/refresh: NÃO ENCONTRADO NA DOC (não há expiração documentada; 401 = chave ausente, 403 = chave inativa).
2. **URL base**: `https://api.feegow.com/v1/api/...` (ex.: `https://api.feegow.com/v1/api/appoints/search`) (https://docs.feegow.com/). `https://api.feegow.com/v1/docs` devolve 403; a doc viva é https://docs.feegow.com/.
3. **Validar credencial / quem sou eu**: não existe endpoint `/me`. Usar `GET /company/list-unity` (lista unidades da licença; opcionais `endereco`, `cep`) ou `GET /appoints/status`; 401/403 identificam token inválido/inativo (https://docs.feegow.com/).
4. **Profissionais e serviços**:
   - `GET /professional/list?ativo=1[&unidade_id=&especialidade_id=]` (`ativo` obrigatório: 0 inativo, 1 ativo; devolve nomes e IDs). Exemplo da doc: `GET https://api.feegow.com/v1/api/professional/list?ativo=1&unidade_id=2&especialidade_id=4`.
   - `GET /specialties/list[?unidade_id=]`.
   - `GET /procedures/list?tipo_procedimento=N` (ou `procedimento_id` se não mandar `tipo_procedimento`; opcionais `unidade_id, paciente_id, especialidade_id, profissional_id, tabela_id, nome_procedimento`; **valores em centavos**). Exemplo: `GET https://api.feegow.com/v1/api/procedures/list?unidade_id=0&paciente_id=15&tipo_procedimento=2&especialidade_id=5&profissional_id=35&tabela_id=123`.
   - Salas/locais: `GET /company/list-local`. Convênios: `GET /insurance/list[?unidade_id=]`. Funcionários (não é profissional): `GET /employee/list?ativo=1`.
   (https://docs.feegow.com/)
5. **Disponibilidade (tem endpoint nativo)**: `GET /appoints/available-schedule?tipo=E|P&especialidade_id=(se tipo=E)|procedimento_id=(se tipo=P)&data_start=dd-mm-YYYY&data_end=dd-mm-YYYY[&unidade_id=&profissional_id=&convenio_id=&age_from=&age_to=]`. Resposta: `content` → chave `profissional_id` (ex.: `"1"`, `"39"`) → chave `local_id` → chave data `YYYY-MM-DD` → array de horários `HH:MM:SS`; cada profissional traz também `age_restriction`. No exemplo da doc `local_id` ora é array ora objeto (tratar os dois). Não tem chave de unidade na resposta: unidade é filtro (`unidade_id`, 0 = matriz). Datas SÓ em dd-mm-YYYY nesse endpoint (https://docs.feegow.com/).
   - Alternativa de derivação / leitura da agenda: `GET /appoints/search?data_start&data_end[&agendamento_id&retorno&profissional_id&paciente_id&unidade_id&local_id&especialidade_id&canal_id&procedimento_id&status_id (alias status_ids, separados por vírgula)&list_procedures=1|0&start&offset]`. Aceita "DD-MM-YYYY" e "YYYY-MM-DD". Campos da resposta (snake_case): `agendamento_id, data ("07-08-2024"), horario ("09:00:00"), status_id, profissional_id, paciente_id`; `procedimentos[]` só com `list_procedures=1` (paginado `start=0`, `offset=50`). Status: `GET /appoints/status`.
6. **Criar agendamento**: exige `paciente_id`.
   - Buscar paciente: `GET /patient/search?paciente_id=|paciente_cpf=|paciente_passaporte=` (ao menos um; opcionais `passaporte_pais_emissor, photo, programa_saude, cache=NONE`); 409 "Paciente não encontrado". `GET /patient/list?telefone=&cpf=&passaporte=&origem_id=&alterado_em=yyyy-mm-dd&data_aniversario=dd-mm&programa_saude=` (paginação `offset`/`limit`).
   - Criar paciente: `POST /patient/create` (Content-Type: application/json) com `nome_completo` (string ≤200, obrigatório) e `cpf` (numérico ≤11, obrigatório na tabela da doc); opcionais `sem_cpf`, `data_nascimento` (yyyy-mm-dd), `genero` (M/F), `celular`, `email`, `convenio_id`. Devolve `paciente_id`; **se já existe paciente igual devolve o id existente, não duplica**.
   - Criar agendamento: `POST /appoints/new-appoint` com `local_id, paciente_id, profissional_id, especialidade_id, procedimento_id, data (dd-mm-YYYY), horario (HH:MM:SS, 24h), valor, plano, convenio_id, convenio_plano_id, canal_id, tabela_id, notas, celular, telefone, email, sys_user, retorno`. Resposta: `{"success": true, "content": {"agendamento_id": 43, "link": ..., "eventos": ...}}`. "Não é permitido criar agendamentos retroativos". Canais: `GET /appoints/list-channel`.
   (https://docs.feegow.com/)
7. **Cancelar / remarcar**:
   - `POST /appoints/cancel-appoint {agendamento_id, motivo_id, obs}` → `{"success": true, "content": "Agendamento cancelado"}`; motivos em `GET /appoints/motives`.
   - `POST /appoints/reschedule {agendamento_id, motivo_id, data (dd-mm-YYYY), horario (HH:MM:SS), obs}` (a doc mostra a mesma resposta "Agendamento cancelado"; erro de copy da doc, confirmar em sandbox).
   - Status: `POST /appoints/statusUpdate {AgendamentoID, StatusID, Obs, HoraChegada?}` (atenção: PascalCase nesse endpoint).
   - Fila: `GET /appoints/queue-position`.
   (https://docs.feegow.com/)
8. **Webhooks**: NÃO ENCONTRADO NA DOC (não há seção de webhooks; só um objeto `webHook` dentro da resposta de cartão de benefícios em `https://cartao-beneficios.feegow.com/external/...`, que não é agenda). Receber cancelamento = polling de `/appoints/search` filtrando por `status_id`.
9. **Rate limit / custo / plano**: NÃO ENCONTRADO NA DOC. Erros documentados: 422 (`{"paciente_id": ["validation.required"]}`), 409 (`{"success": false, "content": "<motivo>"}`), 401 chave não definida no header, 403 chave inativa, 5xx (https://docs.feegow.com/). A Central de Ajuda diz que "Integrações via API são de responsabilidade do cliente" (a Feegow não faz a integração) e não cita preço (https://ajuda.feegow.com/support/solutions/articles/67000714396-como-integrar-o-feegow-via-api-com-outros-sistemas-).
10. **O que NÃO dá / pegadinhas**:
    - Datas em dd-mm-YYYY na escrita (new-appoint, available-schedule, reschedule) e YYYY-MM-DD nas chaves da resposta de disponibilidade.
    - `available-schedule` exige `tipo` E (por especialidade) ou P (por procedimento).
    - Paciente obrigatório antes do agendamento; `cpf` aparece como obrigatório na tabela, existe `sem_cpf` (confirmar em sandbox se aceita sem CPF).
    - Um projeto terceiro (feegow-mcp) relata corrida "available-schedule diz livre, new-appoint devolve 409": tratar 409 como conflito e reconsultar (fonte terceira, não oficial: https://github.com/lab019/feegow-mcp).
    - Pacote oficial Node: https://github.com/feegow/feegow-public-api-node-package (`new FeegowPublicAPI('<x_access_token>')`).
11. **Veredito**: **SIM, viável por token colado** pelo dono (admin do Feegow gera em Configurações → Outras Configurações → API Pública e cola na HUMA). Sem OAuth, sem app, sem revisão. Falta webhook: cancelamento vindo da clínica só por polling.

## 2. Clínica nas Nuvens

1. **Autenticação**: dois níveis juntos.
   - (a) **HTTP Basic** com `client_id:client_secret` (credenciais internas do sistema ou credenciais de parceiro). A doc mostra o formato `{client_id}:{client_secret}` e não diz explicitamente que é base64 (padrão HTTP Basic, confirmar).
   - (b) Header obrigatório em todo endpoint: **`clinicaNasNuvens-cid: <token de integração da clínica>`** ("Token de integração da clínica").
   - Credenciais são emitidas após contratar o módulo API; caminho no painel: **Configurações → Minha Empresa → Integrações → API Clínica nas Nuvens** (https://api.clinicanasnuvens.com.br/ e https://intercom.help/clinicanasnuvens/pt-BR/articles/7240071-api-clinica-nas-nuvens).
   - Validade/refresh: NÃO ENCONTRADO NA DOC.
2. **URL base**: `https://api.clinicanasnuvens.com.br` (basePath `/`). Swagger 2.0 em `https://api.clinicanasnuvens.com.br/swagger-ui.html`, JSON em `https://api.clinicanasnuvens.com.br/v2/api-docs` (título "API Rest - Clínica nas Nuvens", versão "V 1.0"). Formatos: data `yyyy-MM-dd`, hora `HH:mm:ss`, data-hora `yyyy-MM-dd HH:mm:ss`; body sempre JSON; arrays começam em 0; paginação `pagina`/`registrosPorPagina`; respostas paginadas `PageAPI«X»` = `{lista, pagina, totalPaginas}`. Suporte: suporte@clinicanasnuvens.com.br.
3. **Quem sou eu**: `GET /info` → `ClinicaRetornoAPI {nomeFantasia, razaoSocial, cpfCnpj, contato, endereco, horarioInicio, horarioFim, horarios}` (https://api.clinicanasnuvens.com.br/v2/api-docs).
4. **Profissionais/agendas e serviços**:
   - `GET /executor-agenda/lista[?idEspecialidade&idTipoConvenio&nomeContem&somenteAtivos&somenteAtivosNaWeb&somenteProfissionaisSaude&pagina&registrosPorPagina]` → `lista[]{id, idpessoa, nome, ativo, tipoExecutor: PROFISSIONAL|CLIENTE_FORNECEDOR}`. `GET /executor-agenda/{id}`.
   - `GET /tipo-consulta/lista[?nomeContem&somenteAtivos]` → `{id, nome, ativo, reconsulta}` (**sem duração**). `GET /tipo-consulta/{id}`.
   - `GET /tipo-procedimento/lista[?idTipoConvenio&nomeContem&somenteAtivos&tipo=TODOS|SOMENTE_EXAME|EXCETO_EXAME]` → `PageAPI«TipoProcedimentoRetornoAPI»`; `GET /tipo-procedimento/valores-venda`.
   - `GET /local-agenda/lista[?nomeContem&somenteAtivos]` → `{id, nome, cor, ativo}` (obrigatório no agendamento). `GET /local-agenda/{id}`.
   - `GET /especialidade/lista`, `GET /tipo-convenio/lista`, `GET /agenda-rotulo/lista`, `GET /agenda/origem`.
   (https://api.clinicanasnuvens.com.br/v2/api-docs)
5. **Disponibilidade (tem endpoint nativo, semântica não documentada)**: `GET /executor-agenda/disponibilidade?idExecutorAgenda=<int64>&data=yyyy-MM-dd[&dataFim=yyyy-MM-dd&codTipoAtendimento=<int64>]` → array `DisponibilidadeExecutorRetornoAPI {data, horaInicio, horaFim, idTipoConsulta}`; único texto da doc: "Retorna disponibilidade de horários do executor". **A doc não diz se são slots livres ou janelas de trabalho**; validar com conta real. Cruzar com:
   - `GET /agenda/profissional?codExecutorAgenda=<int64>&dataInicial=&dataFinal=[&pagina&registrosPorPagina]` ("Busca agendas resumidas do profissional") → `lista[]{id, data, horaInicial, horaFinal, nomePaciente, status, contatoPaciente{email, telefoneCelular, telefoneComercial, telefoneResidencial}}`.
   - `GET /agenda/lista?dataInicial=&dataFinal=[&codigoPaciente&codigoPessoaExecutor&dataPor=AGENDAMENTO|CRIACAO&pagina&registrosPorPagina]` → `lista[]` de `AgendaFormRetornoAPI {id, status, data, horaInicio, horaFim, idPaciente, idPessoaExecutor, idLocalAgenda, idTipoConsulta, idTipoConvenio, idOrigemPaciente, idRotulo, emailPaciente, telefoneCelularPaciente, encaminhamento, observacoes, procedimentos, urlSalaEspera}`.
   (https://api.clinicanasnuvens.com.br/v2/api-docs)
6. **Criar agendamento**:
   - Paciente antes: `GET /paciente/lista[?cpfCnpj&nomeContem&numeroIdentificacao&dataInicial&dataFinal&dataPor=CRIACAO&somenteAtivos&pagina&registrosPorPagina]` (**sem filtro por telefone**); `GET /paciente/{id}`; `POST /paciente/novo` (`PacienteForm`: obrigatórios `nome`, `dataNascimento`; opcionais `cpfcnpj, contato{telefoneCelular, telefoneComercial, telefoneResidencial, telefoneRecados, email, ramal..., skype}, endereco, estrangeiro, genero, sexo, idNacionalidade, idOrigem, nomeSocial, numeroControle, numeroIdentificacao`); `PUT /paciente/{id}` ("nem todos os campos estão disponíveis para edição"; campos personalizados não integráveis).
   - Convênio do paciente (obrigatório no agendamento): `GET /convenio-paciente/lista`, `POST /convenio-paciente/associar`, `GET/PUT /convenio-paciente/{id}`.
   - `POST /agenda/novo` body `AgendaFormAPI`, obrigatórios **`data, horaInicio, horaFim, idLocalAgenda, idPaciente, idPacienteConvenio, idTipoConsulta, status`**; `status` enum: `AGENDADO, CONFIRMADO, CONFIRMADO_PACIENTE, CANCELADO, CANCELADO_PACIENTE, EM_ESPERA, EM_ANDAMENTO, FINALIZADO, FALTOU, PAGAMENTO, PRE_ATENDIMENTO, REMARCOU`; opcionais `idPessoaExecutor` (o profissional), `idOrigemPaciente`, `idRotulo`, `telefoneCelularPaciente` (≤20), `emailPaciente`, `encaminhamento` (≤150), `observacoes` (≤500), `procedimentos[]{idTipoProcedimento, idEspecialidade, idPromocao, quantidade}`, `salaEspera: CRIAR`, `notificarEmailPaciente, notificarEmailProfissional, notificarSMSPaciente, notificarSMSProfissional, notificarWhatsappPaciente` (booleanos). Não existem `idExecutorAgenda`, `idProfissional`, `codTipoAtendimento` no body.
   (https://api.clinicanasnuvens.com.br/v2/api-docs)
7. **Cancelar / remarcar**:
   - `PUT /agenda/alteracao-status` body `AlteracaoAgendaAPI {idAgenda (int64), status}` (mesmo enum de 12 valores; cancelar = `CANCELADO` ou `CANCELADO_PACIENTE`).
   - `POST /agenda/{id}/remarcar` body `AgendaRemarcacaoFormAPI {novaData, novoHorarioInicial, novoHorarioFinal (obrigatórios), motivo (≤200)}`.
   - Edição completa: `PUT /agenda/{id}` body `AgendaAlteracaoFormAPI` (mesmos obrigatórios do novo: `data, horaFim, horaInicio, idLocalAgenda, idPaciente, idPacienteConvenio, idTipoConsulta, status`).
   - Leitura: `GET /agenda/{id}` (→ `AgendaFormRetornoAPI`), `GET /agenda/{id}/resumida`.
   - Lista de espera: `POST /lista-espera/novo`, `GET/PUT /lista-espera/{id}`.
   (https://api.clinicanasnuvens.com.br/v2/api-docs)
8. **Webhooks**: NÃO ENCONTRADO NA DOC da API (o Swagger não tem nenhum endpoint de webhook/callback; "notificar" só aparece como flags booleanas do agendamento). Existe só uma "URL para integração via webhook" num manual de pagamento do cel_cash/Celcoin, com whitelist de IPs 190.109.113.249 / 190.109.113.240 (https://ajuda-celpayments.celcoin.com.br/post/117), não é agenda. Cancelamento vindo da clínica = polling de `/agenda/lista` (por `dataPor=CRIACAO` ou olhando `status`).
9. **Rate limit / custo / plano**: **120 requisições por token por minuto; acima disso HTTP 429 "Too many requests"** (https://api.clinicanasnuvens.com.br/). Plano: "API para integrações" aparece só no **plano Enterprise** ("Preços especiais", "Vamos conversar"); o plano Essencial (49,50/profissional/mês, mínimo 3, "a partir de R$ 149,50/mês") não lista API; a seção "Recursos extras" avisa "*Recursos poderão ser cobrados à parte" (https://clinicanasnuvens.com.br/planos-e-precos/). A ajuda diz que a credencial sai "após a contratação do módulo API" (https://intercom.help/clinicanasnuvens/pt-BR/articles/7240071-api-clinica-nas-nuvens). Um relato isolado no Reclame Aqui fala em cobrança extra pela liberação da API (não é fonte oficial).
10. **O que NÃO dá / pegadinhas**:
    - Duas credenciais (Basic + header cid).
    - `idPacienteConvenio` obrigatório mesmo para particular (associar convênio "Particular" ao paciente antes via `/convenio-paciente/associar`).
    - `disponibilidade` sem semântica documentada (livre x janela de trabalho).
    - Tipo de consulta não traz duração: a HUMA precisa calcular `horaFim` com a duração cadastrada nela (`huma/core/service_duration.py`).
    - Sem busca de paciente por telefone (só cpfCnpj / nomeContem / numeroIdentificacao).
    - Orçamentos só leitura; campos personalizados não integráveis.
11. **Veredito**: **SIM por credenciais coladas** (client_id, client_secret e o token cid, todos visíveis no painel do dono em Configurações → Minha Empresa → Integrações → API Clínica nas Nuvens), **mas só para clínicas no plano Enterprise com módulo API contratado**. Sem OAuth, sem app, sem revisão. Sem webhook.

## 3. Trinks (salões/barbearias)

1. **Autenticação**: chave estática.
   - Liberação: o responsável precisa ter perfil vinculado ao estabelecimento e pedir pelo **Fale Conosco** informando nome e e-mail do usuário responsável; "em até 48 horas" o token fica disponível em **Minha Área → Meu Cadastro → seção "Token de API Pessoal" → "Gerar token"** (recuperar: "Visualizar token") (https://www.trinks.com/MinhaArea/MeuCadastro; https://trinks.readme.io/reference/introducao; https://trinks.readme.io/reference/autenticacao; https://ajuda.trinks.com/faq-completo-conecta-trinks-e-integracoes; https://ajuda.trinks.com/ativando-o-conecta-trinks-um-guia-de-integracao-via-api-e-webhooks).
   - Headers exatos: **`X-Api-Key: <chave>`** em toda rota (esquema `ApiKeyAuth`) + **`estabelecimentoId: <id>`** (header string, obrigatório em quase todas as rotas; não vai em `/v1/estabelecimentos`) (https://trinks.readme.io/reference/get_v1-profissionais).
   - Validade/refresh: NÃO ENCONTRADO NA DOC (chave "secreta e intransferível"; 401 Unauthorized se ausente/inválida).
2. **URL base**: `https://api.trinks.com` ("Produção"), rotas em `/v1/...` (https://trinks.readme.io/reference/get_v1-estabelecimentos). Índice de toda a referência: https://trinks.readme.io/llms.txt. Paginação: `page` (padrão 1), `pageSize` (padrão e máximo 50); respostas `{page, pageSize, totalPages, totalRecords, data[]}`.
3. **Quem sou eu**: `GET /v1/estabelecimentos[?page&pageSize]` (só `X-Api-Key`) → `data[]{id, nome, cnpj}`; "O `id` de cada um é o valor do cabeçalho `estabelecimentoId` nas demais rotas" (https://trinks.readme.io/reference/get_v1-estabelecimentos). Consumo do mês: `GET /v1/consumo` (https://trinks.readme.io/reference/get_v1-consumo). Detalhe: `GET /v1/estabelecimentos/{estabelecimentoId}`.
4. **Profissionais e serviços**:
   - `GET /v1/profissionais[?page&pageSize&status=1 Ativo (padrão)|2 Inativo|3 Todos&include=1 (Foto)]` → `data[]{id, idProfissional, nome, apelido, cpf, genero (M/F/N/X), status, possuiAgenda, fazLancamentoPAT, codigoIdentificacao, formaRelacaoProfissional, funcao, dataInicio, dataFimContrato, dataInativacaoUnidade, perfilAcesso, fotoUrl}`. **Usar `id`** ("é o id usado nas demais rotas", agendamentos, comissões); `idProfissional` é o cadastro geral (aparece em `/v1/transacoes`), NÃO usar em `profissionalId` de agendamento (https://trinks.readme.io/reference/get_v1-profissionais).
   - `GET /v1/profissionais/{profissionalId}/servicos` (serviços do profissional). `GET /v1/profissionais/{servicoCategoriaEstabelecimentoId}` (por categoria de serviço).
   - `GET /v1/servicos[?page&pageSize&nome&categoria&somenteVisiveisCliente=false]` → `data[]{id (= servicoId dos agendamentos), nome, duracaoEmMinutos, preco (tabela em reais, sem promoção), categoria, valorPromocional (promoção do dia da semana atual), tipoPreco}`; só ativos, ordenados por nome. Promoções por dia: `GET /v1/servicos/{id}/promocoes` (https://trinks.readme.io/reference/get_v1-servicos).
5. **Disponibilidade (tem endpoint nativo de slots)**: `GET /v1/agendamentos/profissionais/{data}` com `data` em `AAAA-MM-DD` (path, obrigatório); query opcionais: `intervalos` (int, 5 a 120; "Minutos entre um horário sugerido e o próximo"; default = configuração do profissional/estabelecimento ou 60), `servicoId` ("Restringe aos profissionais que fazem o serviço e usa a duração dele"), `servicoDuracao` ("Duração em minutos que precisa caber em cada horário. Tem prioridade sobre a duração do serviço"), `profissionalId` (campo `id` de `GET /v1/profissionais`), `page` (50 profissionais por página, por nome; sem `pageSize`), `excluirExcecoesDeAgendamentoOnline` (true = só profissionais habilitados para agendamento online). Resposta `ProfissionalComAgendaDTOPagedList {page, pageSize, totalPages, totalRecords, data[]{id, nome, horariosVagos: ["HH:mm", ...], intervalosVagos: [{inicio: "HH:mm", fim: "HH:mm"}]}}`. Regras da doc: "`horariosVagos` traz os inícios possíveis no dia, de `intervalos` em `intervalos` minutos a partir da abertura do estabelecimento"; `intervalosVagos` = "Faixas livres do profissional no dia, já sem agendamentos, ausências e intervalos"; prioridade de duração: `servicoDuracao` > duração do `servicoId` > o próprio intervalo; profissional que não trabalha no dia vem com listas vazias; **"Não há filtro de antecedência: para hoje, horários que já passaram também aparecem"** (filtrar na HUMA). **Um dia por chamada** (https://trinks.readme.io/reference/get_v1-agendamentos-profissionais-data). Configurações da agenda: `GET /v1/agendamentos/configuracoes`. Lista de agendamentos: `GET /v1/agendamentos`; detalhe `GET /v1/agendamentos/{id}` (traz `cancelamento` e `observacoesDoEstabelecimento`).
6. **Criar agendamento**:

Resposta `201 {id}`; `400 {Message: "Invalid request.", Errors[{PropertyName, ErrorMessage}]}` (às vezes `PropertyName` é o nome interno, ex.: `ServicoEstabelecimentoId` = `servicoId`). **"A API não verifica conflito de horário nem disponibilidade.    - **Consentimento**: `Calendars.ReadWrite` delegada é permissão que o próprio usuário consente por padrão ("By default, all users are allowed to consent to applications for permissions that don't require administrator consent. For example, by default, a user can consent to allow an app to access their mailbox"); o admin do tenant pode restringir a política para "verified publishers, for selected permissions" (`microsoft-user-default-low`) ou desligar consentimento de usuário, aí entra admin consent / admin consent workflow (https://learn.microsoft.com/en-us/entra/identity/enterprise-apps/configure-user-consent).
   - **Publisher verification**: não obrigatório, mas "Beginning November 2020, if risk-based step-up consent is enabled, users can't consent to most newly registered multitenant apps that aren't publisher verified" quando o app pede além de sign-in/perfil e o usuário está em tenant diferente do que registrou o app (aparece aviso de "unverified publisher"). Requisitos: conta Microsoft AI Cloud Partner Program (ex-MPN) verificada com Partner One ID (conta global), app registrado com conta work/school num tenant associado ao PGA, publisher domain configurado (não `*.onmicrosoft.com`; o domínio do e-mail da verificação tem que bater ou ser domínio custom verificado no tenant), usuário com Application Administrator/Cloud Application Administrator + Partner Center Admin, MFA; "verified in minutes"; grátis (https://learn.microsoft.com/en-us/entra/identity-platform/publisher-verification-overview).
   - Não há revisão/aprovação da Microsoft para permissões delegadas de calendário.
2. **URL base**: `https://graph.microsoft.com/v1.0`.
3. **Quem sou eu**: `GET /me` → `{id, displayName, mail, userPrincipalName, mobilePhone, preferredLanguage, ...}` (https://learn.microsoft.com/en-us/graph/auth-v2-user). Calendários: `GET /me/calendars`. Fusos suportados: `GET /me/outlook/supportedTimeZones`.
4. **Profissionais e serviços**: não existe conceito de serviço. "Profissional" = usuário/mailbox (`/me` ou `/users/{id|userPrincipalName}`) e, opcionalmente, um calendário (`/me/calendars/{id}`). Para a HUMA, cada profissional é um login Microsoft (um OAuth por pessoa) ou um calendário escolhido dentro da conta do dono.
5. **Disponibilidade**:
   - **`POST /me/calendar/getSchedule`** (ou `/users/{id|upn}/calendar/getSchedule`; equivalente do FreeBusy) headers `Content-Type: application/json`, `Prefer: outlook.timezone="E. South America Standard Time"`; body `{schedules: ["email@dominio"], startTime: {dateTime: "2026-11-10T08:00:00", timeZone: "E. South America Standard Time"}, endTime: {...}, availabilityViewInterval: 30}` (intervalo 5..1440, default 30) → `200 {value: [{scheduleId, availabilityView: "000220130" (0 free, 1 tentative, 2 busy, 3 oof, 4 workingElsewhere), scheduleItems: [{status: busy|free|tentative|oof|workingElsewhere, subject?, location?, isPrivate?, start{dateTime,timeZone}, end{...}}], workingHours: {daysOfWeek[], startTime, endTime, timeZone{name}}}]}`; permissão mínima `Calendars.ReadBasic` (delegada work/school ou application); **"Delegated (personal Microsoft account): Not supported"**; erro 5006 se mais de 1000 itens no período (https://learn.microsoft.com/en-us/graph/api/calendar-getschedule?view=graph-rest-1.0).
   - Conta pessoal (Outlook.com/Hotmail) ou fallback: `GET /me/calendarView?startDateTime=2026-11-10T00:00:00-03:00&endDateTime=2026-11-11T00:00:00-03:00` (ISO 8601 com offset; sem offset = UTC; suporta `$select`, `$top`; `Prefer: outlook.timezone`; permissão `Calendars.ReadBasic`, **suporta conta pessoal**) → `value[]` de eventos (`start`, `end`, `showAs`, `isCancelled`, `subject`, ...) e derivar livre = janela de trabalho cadastrada na HUMA menos esses eventos (https://learn.microsoft.com/en-us/graph/api/user-list-calendarview?view=graph-rest-1.0).
   - Sugestão de horários: `POST /me/findMeetingTimes` body `{attendees: [] (vazio = só o organizador), timeConstraint: {activityDomain: work|personal|unrestricted, timeSlots: [{start{dateTime,timeZone}, end{...}}]}, meetingDuration: "PT30M", maxCandidates, minimumAttendeePercentage, returnSuggestionReasons, isOrganizerOptional}` → `meetingTimeSuggestions[]{confidence, meetingTimeSlot{start,end}, ...}` + `emptySuggestionsReason`; permissão `Calendars.Read.Shared`; **só work/school (conta pessoal e application: Not supported)**; `work` = horário de trabalho do mailbox (default seg-sex 8-17) (https://learn.microsoft.com/en-us/graph/api/user-findmeetingtimes?view=graph-rest-1.0).
6. **Criar agendamento**: `POST /me/events` (ou `/me/calendar/events`, `/me/calendars/{id}/events`, `/users/{id|upn}/events`); permissão `Calendars.ReadWrite` (delegada work/school **e pessoal**, ou application); headers `Content-Type: application/json`, `Prefer: outlook.timezone="E. South America Standard Time"`; body mínimo `{subject: "Corte - João (11 99999-9999)", body: {contentType: "HTML"|"Text", content: "..."}, start: {dateTime: "2026-11-10T14:00:00", timeZone: "E. South America Standard Time"}, end: {dateTime: "2026-11-10T14:30:00", timeZone: "E. South America Standard Time"}, location: {displayName: "..."}, attendees: [{emailAddress: {address, name}, type: "required"}], allowNewTimeProposals, transactionId: "<uuid>"}` → `201` + objeto `event {id, iCalUId, webLink, ...}`. `transactionId` evita duplicar em retry. **"When you create an event that includes attendees, the server sends invitations to all attendees... can't be configured"**: lead sem e-mail = não pôr attendee (guardar nome/telefone em `subject`/`body`). Usar só fusos de `supportedTimeZones` (https://learn.microsoft.com/en-us/graph/api/user-post-events?view=graph-rest-1.0). Não existe "cliente" a criar antes.
7. **Cancelar / remarcar**:
   - `DELETE /me/events/{id}` (também `/users/{id|upn}/events/{id}`, `/me/calendars/{id}/events/{id}`) → `204 No Content`; se for reunião, manda cancelamento aos attendees (https://learn.microsoft.com/en-us/graph/api/event-delete?view=graph-rest-1.0). 404 em delete de evento já apagado (mesma idempotência do Google).
   - `PATCH /me/events/{id}` body só com o que muda, ex. `{start: {dateTime, timeZone}, end: {dateTime, timeZone}}` (campos editáveis: attendees, body, categories, end, hideAttendees, importance, isAllDay, isOnlineMeeting, isReminderOn, location, locations, onlineMeetingProvider, recurrence, reminderMinutesBeforeStart, responseRequested, sensitivity, showAs, start, subject) → `200` + evento; update de attendees manda e-mail só aos que mudaram (https://learn.microsoft.com/en-us/graph/api/event-update?view=graph-rest-1.0).
8. **Webhooks (change notifications)**:
   - `POST https://graph.microsoft.com/v1.0/subscriptions` body `{changeType: "created,updated,deleted", notificationUrl: "https://app.humaia.com.br/webhook/microsoft", lifecycleNotificationUrl: "https://app.humaia.com.br/webhook/microsoft/lifecycle" (opcional, recomendado), resource: "me/events" (ou "users/{id}/events"), expirationDateTime: "<ISO UTC>", clientState: "<segredo>", latestSupportedTlsVersion: "v1_2"}` → `201 {id, resource, applicationId, changeType, clientState, notificationUrl, expirationDateTime, creatorId, notificationContentType}`; permissão `Calendars.Read` (delegada work/school **e pessoal**, ou application); delegada só assina o mailbox do usuário logado; 409 `Subscription Id <> already exists for the requested combination` se duplicar changeType+resource (https://learn.microsoft.com/en-us/graph/api/subscription-post-subscriptions?view=graph-rest-1.0).
   - **Validação do endpoint na criação**: Graph faz `POST {notificationUrl}?validationToken=<token>` com `Content-Type: text/plain; charset=utf-8` e exige em **10 s**: `200 OK`, `Content-Type: text/plain`, corpo = token **URL-decodificado em texto puro** (codificado = falha; falha = subscription não criada, 400). Se tiver `lifecycleNotificationUrl`, valida também.
   - **Notificação**: `POST {notificationUrl}` body `{value: [{id?, subscriptionId, subscriptionExpirationDateTime, clientState, changeType: created|updated|deleted, resource: "users/{user}/events/{id}", tenantId, resourceData: {"@odata.type": "#Microsoft.Graph.Event", "@odata.id", "@odata.etag", id}}]}` (pode trazer várias de várias subscriptions no mesmo POST); **responder 2xx em 3 s** (200 se processou; senão enfileirar e `202 Accepted`); non-2xx/timeout = retry exponencial por até 4 h (timeout 10 s nos retries); endpoint "slow" (>10% acima de 3 s em 10 min) atrasa 10 min; "drop" (>15% acima de 10 s) descarta por 10 min; validar `clientState` sempre; payload básico NÃO traz o evento (buscar `GET /me/events/{id}`); query string da `notificationUrl` é repassada (https://learn.microsoft.com/en-us/graph/change-notifications-delivery-webhooks).
   - **Expiração máxima para `event`: 10.080 min (menos de 7 dias)**; renovar com `PATCH /subscriptions/{id} {expirationDateTime}` → 200; apagar `DELETE /subscriptions/{id}` → 204; latência do calendário média < 1 min, máx. 3 min; máx. 1.000 subscriptions ativas por mailbox; subscription traz um access token próprio para o endpoint que expira ~1 h e é renovado com a subscription (lifecycle notifications avisam `reauthorizationRequired`, `subscriptionRemoved`, `missed`) (https://learn.microsoft.com/en-us/graph/change-notifications-overview; https://learn.microsoft.com/en-us/graph/change-notifications-lifecycle-events).
9. **Rate limit / custo / plano**: Outlook: **10.000 requisições por 10 min por combinação app+mailbox, 4 requisições concorrentes por mailbox**, 150 MB upload por 5 min; global 130.000 req/10 s por app em todos os tenants; subscriptions: 500 POST/PATCH/DELETE por 20 s por app por tenant (2.000 por app no total), `GET /subscriptions` lista 25/20 s (https://learn.microsoft.com/en-us/graph/throttling-limits). Sem custo da API; publisher verification grátis; registrar app exige um tenant Entra (conta Azure gratuita serve). Funciona para Microsoft 365 (work/school) e contas pessoais Outlook.com.
10. **O que NÃO dá / pegadinhas**:
    - `getSchedule` e `findMeetingTimes` não funcionam em conta pessoal (Outlook.com/Hotmail) → caminho `calendarView` para derivar.
    - Attendees disparam e-mail automático de convite/cancelamento/atualização (lead sem e-mail = sem attendee).
    - Subscription expira em menos de 7 dias: job de renovação obrigatório (padrão `instagram_token_refresh`/`mercadopago_token_refresh` do scheduler).
    - Payload do webhook não traz o evento (segunda chamada `GET /me/events/{id}`); `deleted` não permite ler o evento, guardar o `id` no `active_appointment_event_id`.
    - Tenants corporativos podem exigir admin consent ou bloquear app sem publisher verification (tela "unverified publisher").
    - Refresh token morre com 90 dias de inatividade (renovar periodicamente, não só quando o lead agenda).
    - Timezone no formato Windows ("E. South America Standard Time"), não IANA; `calendarView` aceita offset ISO.
    - `getSchedule` por e-mail SMTP de colega só mostra o que a política de free/busy do tenant permite.
    - Conta pessoal: subscription em `user` não suportada, mas em `event` sim.
11. **Veredito**: **NÃO por token colado** (não existe token estático). **SIM por OAuth** sem revisão da Microsoft: HUMA registra app multitenant+pessoal no Entra (https://entra.microsoft.com → App registrations), plataforma Web, redirect `https://app.humaia.com.br/oauth/microsoft/callback`, client secret (renovar a cada ≤ 12-24 meses), escopos delegados `offline_access User.Read Calendars.ReadWrite`, tenant `common`. Admin consent NÃO é exigido por padrão para `Calendars.ReadWrite` delegada, mas conta corporativa pode cair em tenant que bloqueia app não verificado: fazer **publisher verification** (Partner Center + domínio humaia.com.br no tenant) antes do piloto com clientes M365.

## Resumo comparativo (para decisão)

| | Feegow | Clínica nas Nuvens | Trinks | Calendly | Microsoft Graph |
|---|---|---|---|---|---|
| Credencial | token colado (admin gera) | Basic client_id/secret + header cid (Enterprise) | X-Api-Key colada (liberação 48h) + estabelecimentoId | PAT colado ou OAuth PKCE | só OAuth (app no Entra) |
| Slots livres nativos | sim (`available-schedule`) | semi (`disponibilidade`, semântica não documentada) | sim (`profissionais/{data}`, 1 dia/chamada) | sim (`event_type_available_times`, 31 dias) | free/busy (`getSchedule`; conta pessoal = `calendarView`) |
| Cria sem e-mail do lead | sim (cpf/`sem_cpf`) | sim (nome + nascimento) | sim (telefone) | **não** (e-mail obrigatório) | sim (sem attendee) |
| Remarcar por API | sim (`reschedule`) | sim (`remarcar`) | sim (PUT completo) | **não** | sim (PATCH) |
| Webhook de cancelamento | não | não | sim (SNS; cadastro via Trinks) | sim (`invitee.canceled`) | sim (renovar < 7 dias) |
| Limite | não doc. | 120/min | 60/min e **5.000/mês** | 500/min; `POST /invitees` 100/dia (Free 5/dia) | 10.000/10 min por mailbox |
| Plano | não doc. | Enterprise + módulo API | "serviço adicional" (preço sob consulta) | Free serve | qualquer M365/Outlook.com |
